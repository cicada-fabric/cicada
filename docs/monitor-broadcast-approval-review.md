# Monitor broadcast preview and Codex approval review

Status as of 2026-09-27: the Node-local read-only preview is implemented and its clean-candidate deterministic gates pass. In the controlled Android/native run, the original Monitor Thread completed one preview and one separately reviewed dispatch; both original recipient Threads passed receive/context assertions. Client's final strict status, Core's scoped ciphertext scan, Intake's independent Hub audit and owned-fixture cleanup passed. Exact evidence and limits are in the [25013b5 candidate record](client-hub-v13-25013b5-validation.md), [fixed-Hub run procedure](client-monitor-native-fixture.md), and [Client validation report](../../CICADA_CLIENT/docs/client-monitor-v13-25013b5-native-validation.md).

The Android `monitor.broadcast_confirm` is the existing user authorization for one exact, consent-bound payload and ordered recipient scope. The new `cicada_monitor_broadcast_preview(approval_id)` uses the original Monitor native session and current authorization checks to verify the Owner/Client evidence and decrypt the exact body locally for review. Its structured result reports the bound body, ordered targets, expiry and consent evidence. It does not create another user approval, make tool output a user decision, or authorize delivery by itself. The later `cicada_monitor_broadcast(approval_id)` must use the same original approval ID and remains subject to the current Hub/Node Guard and its own Codex review.

## What the pinned Runtime evidence establishes

The locally pinned Codex image is `sha256:742214d7f2b7f0cd6a4f5bd5ed1d55d0026c25de0f654dc868cfdf70882cf264`, with CLI `0.157.1`. Offline `codex --version` and `codex exec --help` both exited `0`; the latter describes `--approve-for-me` as routing approval requests through automatic review. A separate no-model probe in `.cicada-data/monitor-approval-review-baseline-70fc988/codex-cli-tool-isolation-0.157.1.json` confirmed that this CLI accepts `mcp_servers.cicada.enabled_tools` and that `exec resume` accepts per-turn config/feature flags. The native fixture configures only the preview tool on the preview turn and only the dispatch tool on the later dispatch turn, while disabling shell, unified exec, apps, browser use and web search. These are test-scoped CLI options, not a product-level isolation guarantee. No model was invoked during those probes and no global config or approval policy was changed.

OpenAI's Auto-review documentation says a reviewer receives a compact transcript with the exact approval request and typically relevant tool calls and outputs. It may perform read-only checks to gather missing context, but does so rarely. This means a same-Thread preview output can be relevant context; the documented behavior does not guarantee that every earlier field will be retained, that the reviewer will treat tool output as authoritative proof, or that the action will be approved. Only a real, controlled preview-then-send attempt can answer whether the actual reviewer accepts this flow. An explicit denial means stop; the documented response is to find a materially safer alternative or ask the user, not to reach the same outcome through a workaround.

The app-server documentation distinguishes local MCP server elicitation (`mcpServer/elicitation/request`) from app-connector tool-call approvals (`tool/requestUserInput`). The latter is documented for Apps/connectors and cannot be assumed to provide a user prompt for this local stdio MCP tool. On the repository baseline, `cicada-go/internal/control/appserver.go` handles command/file approval requests and MCP server elicitation in the Control app-server path. The Node `machineApprovalBridge` in `cicada-go/cmd/cicada/machine_codex_approval.go` accepts command/file approval request methods only; it is not an interactive approval bridge for this MCP broadcast. No local source or pinned CLI help establishes such a bridge for the Monitor tool.

The preview tool is annotated read-only and idempotent, with `destructiveHint=false` and `openWorldHint=false`. MCP annotations are presentation/routing hints, not proof of what the tool did and not authorization; the server still enforces its checks. The fixture also checks the observed transcript for unexpected actions, but that assertion does not provide general prompt-injection isolation. The approved body remains untrusted message content.

## Required preview and dispatch boundary

The preview uses the original Monitor Endpoint and approval ID, current Guard, and exact durable approval record. It shows the verified body, ordered destinations, expiry, and the relevant signed Owner/Client authorization facts without asking the model to infer them from an ID or alias. The body remains untrusted message content, not instructions. Preview does not call dispatch authorization, mutate approval or outcome state, consume a replay counter, create an outbox entry, or inject/send a message. Clean-candidate tests verify that the review leaves approval, replay, outbox, and delivery ledgers unchanged and fails closed for wrong Node/session, expiry, revocation, or altered evidence.

The real dispatch remains a separate operation with the same original approval ID and current Guard. Do not change its body, recipient scope, seal, or approval identity after preview. If Codex auto-review denies the dispatch before MCP execution, record that denial, verify that no outbox or child delivery was created, and stop this fixture. Do not repeat the call, reseal the payload, prompt around the denial, change reviewer policy, or use approval-bypass options. A denial is not an app-level user's explicit decision to authorize the broadcast.

The completed run showed the reviewer-facing preview and exact send call on the same original Thread, with the same approval ID, followed by independently verified Hub and recipient outcomes. This evidence is limited to this controlled run. Reviewer acceptance alone is not delivery; an Android Confirm or a tool transcript alone is not recipient consumption. The two logical Nodes shared one container; physical dual-Node operation, public HTTPS, and full product-facing React Native consent UX remain **NOT_RUN**. This is not a general prompt-injection defense.
