## Codex app-server: queue acceptance is not native execution

The pinned Codex protocol exposes `thread/queue/add`, `list`, `update`, `delete`, `reorder`, and `start`; the queue methods are explicitly marked **experimental** in [`common.rs`](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/app-server-protocol/src/protocol/common.rs). `thread/resume` prefers a stable `thread_id`; optional history/path resume inputs are unstable. The API returns a queued submission identity that can be reconciled with the queue list.

The important cold-session behavior is deliberate: queue add persists input and wakes/dispatches a thread only if the app-server already has it loaded. The pinned [queue service](https://github.com/openai/codex/blob/rust-v0.156.1/codex-rs/ext/queue/src/service.rs) returns without dispatch when `get_thread` cannot find a loaded instance; `thread/queue/start` is documented as starting selected work only when its thread is idle. In official [issue #44491](https://github.com/openai/codex/issues/44491), an OpenAI maintainer confirmed that leaving a cold thread's item pending is the intended queue contract and recommended explicitly resuming it. Therefore a successful `codex queue --thread` or `thread/queue/add` is only queue acceptance, not model consumption or completion.

There is a second operational risk: resuming a very large history has had upstream-reported latency and memory failures ([#38787](https://github.com/openai/codex/issues/38787), [#30932](https://github.com/openai/codex/issues/30932)). Treat those as failure cases to measure against the pinned CLI, not as a permanent claim about every version. Use metadata-only/paginated resume where supported, coalesce retries for one thread, and preserve a timeout/unknown state instead of starting a duplicate session.

Current CICADA evidence:

- [`machine_fabric.go`](../cicada-go/cmd/cicada/machine_fabric.go) invokes `codex queue --thread <native-id> --message ...` for Fabric delivery. This preserves the target Thread ID but does not resume a cold Thread.
- [`internal/codexapp/client.go`](../cicada-go/internal/codexapp/client.go) launches the official `codex app-server --stdio`; it is a small request/event transport today and does not implement native Fabric queue lifecycle methods.
- [`machine_codex_approval.go`](../cicada-go/cmd/cicada/machine_codex_approval.go) already uses `thread/resume` for the Node approval flow and checks the returned native Thread identity.
- The native evidence in [`architecture-v2-status.md`](architecture-v2-status.md) and [`architecture-v2-native-validation.md`](architecture-v2-native-validation.md) records explicit resume by the test driver. It does not establish unattended wake for a cold session.

**Next concrete integration:** extend the existing Node-side Go app-server boundary with a version/capability-gated, single-reader JSON-RPC client for queue add/list/start and exact-ID resume. Bind it to the current SessionBinding lease/epoch; resume only Cicada-owned or explicitly adopted sessions at an approved safe point, verify the returned ID, and start a selected queued submission only when the exact thread is idle. Persist CICADA's own delivery/request identity before calling Codex and reconcile it against Codex's queue ID/events after restart. If native consumption cannot be observed, retain `CONSUMPTION_UNCONFIRMED`; if injection may have happened before CICADA recorded it, retain `INJECTION_UNCERTAIN`. The first gate should cover a real pinned Codex CLI plus a fake app-server protocol test for cold queue, duplicate retry, busy/approval-waiting thread, wrong ID, stale lease and restart. This adds no Go module dependency and keeps current durable Node inbox/outbox authoritative.

The queue/resume API's experimental status means CICADA must pin and test the CLI version, opt in to experimental app-server methods only in the compatible initialization handshake, reject unsupported methods, and keep existing `codex queue` behavior until the adapter passes the gate. It must not infer user authorization from a peer message or resume an interactive user-owned Thread without the adopted-session lease.

## Happy: focused app-server implementation reference

At the pinned Happy commit, [`codexAppServerClient.ts`](https://github.com/slopus/happy/blob/3825130467cb6e8fd49205f2aadbc3d5d83e9019/packages/happy-cli/src/codex/codexAppServerClient.ts) owns child-process startup, the initialize handshake, request correlation, server events/requests, and process epochs. [`runCodex.ts`](https://github.com/slopus/happy/blob/3825130467cb6e8fd49205f2aadbc3d5d83e9019/packages/happy-cli/src/codex/runCodex.ts) connects that transport to resume/fork, turn lifecycle, permissions, and daemon supervision. Its MIT license requires retaining the notice when copying or deriving code.

This is useful as a behavior checklist for the Go adapter: one owner for stdout/event demultiplexing, explicit process generation, pending request correlation, original native Thread ID, server-to-client approval handling, turn completion/error tracking, and restart reconciliation. It is not a drop-in dependency: CICADA is Go, already has `internal/codexapp`, and must preserve its own SessionBinding lease, Guard, Node inbox/outbox, and approval authority. The existing [`docs/upstream-happy.md`](upstream-happy.md) pins the same commit and lists the reviewed files; this note narrows reuse to the app-server boundary.

## CIRCL: retain current PQ provider and trust state

[`internal/e2ee/pq.go`](../cicada-go/internal/e2ee/pq.go) imports CIRCL `mlkem768` and `mldsa65`; [`ratchet.go`](../cicada-go/internal/e2ee/ratchet.go), endpoint grants, and attestations use the same provider. `go.mod` already pins v1.6.5, whose official release includes stricter key/signature parsing fixes. The upstream README lists ML-KEM parameter sets under FIPS 203 and ML-DSA under FIPS 204, while warning that CIRCL is supplied as-is and that not every package is constant-time.

No provider swap belongs in the Group/session migration: existing public-key encodings, signatures, persisted identities, Contact pins, ratchet/replay counters, and test vectors must remain interoperable. CIRCL's BSD-3-Clause license is compatible with the current dependency use; if source is copied or vendored, preserve its notice. Use of NIST algorithm implementations does not by itself establish FIPS 140 validation, whole-protocol review, or Hub-blind end-to-end delivery; see [`docs/e2ee.md`](e2ee.md) and [`architecture-v2-pq-transport.md`](architecture-v2-pq-transport.md) for current termination boundaries.

## Modern SQLite: keep the current store and migration path

The repository already pins `modernc.org/sqlite v1.59.0` and its required `modernc.org/libc v1.75.7`. Upstream describes this driver as a CGo-free Go port and records SQLite 3.53.4 for the supported platforms. SQLite's upstream release history lists 3.53.4 as the current SQLite release at this review date. The driver has a BSD-style license; the SQLite engine is public domain. Upstream warns that the translated core is slower than native C for CPU-bound work and requires applications to keep the libc version matched to the driver's `go.mod`.

[`internal/store/store.go`](../cicada-go/internal/store/store.go) already uses `database/sql`, WAL, `busy_timeout`, and foreign keys. [`internal/store/migrations_v2.go`](../cicada-go/internal/store/migrations_v2.go) owns a checksummed additive migration ledger at schema v30; [`state_backup.go`](../cicada-go/internal/store/state_backup.go) verifies SQLite integrity and foreign-key state during backup/recovery. This is enough for the current single-Hub/Node durability model; no upstream evidence in this review justifies PostgreSQL, Redis, or a separate queue service. Revisit only with measured contention/capacity limits or a required multi-writer deployment, and benchmark against CICADA's real query shapes before changing drivers.
