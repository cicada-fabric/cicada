# Same-Node Group messages default to Hub Relay

This candidate starts from `144e079`. Equal Node IDs are routing labels, not proof of the same physical host, authenticated Codex account or usable native direct API. New ordinary same-Group MCP SEND, ASK, REPLY and broadcast children therefore use the existing sealed Hub Relay even when both Endpoints share a Node. Generic native direct SEND/ASK creation returns the Node-origin `UNSUPPORTED` error. No model field, Unix UID or local session metadata can enable direct eligibility.

The existing Owner key grants, current Endpoint candidates/pins, membership and join revisions, bindings, leases, Network/Group Guard, ciphertext format and fixed same-Group data scope remain authoritative. Joining still grants no peer/history permission. Distinct Endpoints are required; self delivery and self pins remain denied. No RPC, table, crypto profile, dependency or Client contract change is introduced (wire 1 and 55 operations/schema 55). The combined Main candidate is `v1.6.2` due to the separate explicit directory permission slice; this transport correction adds no operation.

The Node derives each native caller from its current joined Session and rechecks the exact native binding. Hub status is returned only to either original Endpoint; only the original receiver can reply and only the original sender can cancel. Sharing a Principal or Node does not inherit those identities. Cancellation reads and checks the original sender's Endpoint, Principal, binding and epoch before POST; rejected callers do not post cancellation or change the request/timestamps or cryptographic state. A successful user cancellation does not prove that a Runtime has stopped.

Causal ASK remains bound to an open, received parent and its current binding, scope and bounded ancestry. Same-Node B→C may inherit an eligible A→B parent; A→B→A remains denied. REPLY ciphertext inherits the original stored causal parent, never a model-supplied parent, and retains request/message correlation.

Existing Node-local durable messages are retained. Before creating Relay work, the Node reads the old ledger in SQLite `mode=ro`; only a reliable missing file/row permits a new Relay operation. Exact historical SEND/ASK replay authenticates the old ciphertext/body and compares operation ID, kind, deadline, current keys, complete route and native binding. It neither seals again, advances crypto/replay counters nor wakes/reinjects the queue. Corrupt, inaccessible, mismatched or unverifiable records fail closed. Old local ledgers never persisted the previously unused caller `IdempotencyKey`; this change does not claim a historical match of that field or infer a missing causal parent. Legacy reply/status/cancel retain their separate ledger path with a read-only original-caller check before mutable ledger helpers. Advisory/SQLite read operations are not a claim of zero OS metadata effects. No automatic local-to-Relay migration occurs.

Broadcast uses the immutable existing recipient/key/binding snapshot. New children use Relay; an exact historical local child can return its recorded result only after current Guard and snapshot checks. Unknown or uncertain local history is not re-sealed or blindly sent through Relay. Current authorization remains per child; a parent or another Group does not confer a grant.

Monitor broadcast outcomes now follow the dispatch's verified internal transport evidence, rather than equal Node IDs. The Hub accepts `RELAY_PERSISTED` for either Node route only after matching the persisted sealed security record, route, payload digest and recipient outbox. Missing or corrupt evidence fails closed. `NODE_REPORTED` remains limited to authenticated exact historical local replay. No caller JSON field supplies this internal evidence, and retries cannot create a Relay child after uncertain local history.

A lost outcome ACK followed by a temporary sealed SEND 503 can leave the Hub's original Relay child ACCEPTED while the current Node attempt remains UNKNOWN. The Node accepts that correlated higher durable receipt without an ACK mismatch or discarded batch progress. Two ACCEPTED reports still require identical verified evidence; wrong message IDs, invalid evidence and a lower report against Node-only evidence fail closed. The MCP result stays UNKNOWN/retryable until the same operation succeeds. Acceptance describes transport persistence, not native consumption.

Task handoff's existing same-Node local path/state machine is outside this slice and remains a separate follow-up. The recording queue fixtures verify protocol routing and guards only. They do not establish real native consumption, authenticated native account/direct eligibility, Android, PQ-TLS, public HTTPS or physical-device results.
