## Regroup-specific review rules

The pinned Core Store binds a proposal to its Hub, Human Group Owner, Network, exact source/target Groups, action, expected source/target `version`s, Monitor Endpoint, Monitor Principal, Node binding ID and binding epoch. It is created by an authenticated Monitor actor and expires 24 hours after creation. `SET_PARENT` requires distinct source/target Groups and no new name; `CREATE_CHILD` requires a non-empty trimmed name of at most 80 characters. Both source and target must be ACTIVE, same Hub/Network/Owner/trust domain, and currently visible to the Monitor. Before issue, Core's current Guard additionally requires an explicit current Monitor Membership in the target Group and its revision; Group existence does not imply Membership. No topology changes at proposal creation.

Issuing delegation requires the exact proposal still be `PROPOSED`, unexpired, same Hub/Owner/Network, and both ACTIVE Group versions unchanged. Delegation expiry must be future and at most 24 hours away; it must also be no later than proposal expiry. It is exact-scope, `max_uses=1`, and initially `ACTIVE`, version 1. Native Monitor application independently rechecks the current Monitor role, Endpoint/Principal/Binding/epoch, source and target membership, current Group versions, expiry and the exact proposal/delegation tuple, then consumes the delegation once. Revocation is an Owner-issued version-CAS state change; the server permits only the current `ACTIVE` version.

`RegroupProposalResult.owner_id` is the Group's Human Owner principal. `principal_id`, `endpoint_id`, `binding_id` and `binding_epoch` identify the Monitor actor; they must not be collapsed into or presented as the Owner. Regroup Owner actions use the accepted encrypted Client-device request and explicit phone confirmation. The contract does not call for an offline external Owner proof on top of that authenticated request. By contrast, cross-Owner key consent, Network collaboration grants, Link key grants, and Link review-policy grants explicitly require independent Owner signatures as described above.

For a lost delegation issue/revoke response, recover the exact original packet while it remains pending. A validated cached/recovered `COMPLETED` response can clear that pending operation and its write context. If authenticated recovery returns terminal `OUTCOME_UNCERTAIN`, retain the original ciphertext/counters and keep the dedicated regroup fence blocked indefinitely: the current Core contract defines no later correlated success or manual/automatic clearing route. After the transport slot is resolved, `topology.regroup_proposal` may inspect the optional current delegation, but that metadata has no original device request/operation correlation and cannot clear the fence or authorize replacement. Any future reconciliation requires a separately authorized Core contract.

## Public-vector and lifecycle limits

Relevant bundled vectors are synthetic: `cross-owner-group-key-v2.json`, `endpoint-key-attestation-v1.json`, `network-collaboration-key-consent-v1.json`, `network-collaboration-broadcast-consent-v1.json`, and `owner-link-review-policy-proof-v1.json`. They validate canonical serialization, purpose separation, signatures or attestation parsing under test keys. They do not bind fields to a real current Owner, Network, native Thread, Node or SessionBinding. There is no equivalent public cryptographic vector for regroup proposal/delegation authority or the Link-key manifest/grant chain. The pinned Store test `delegated_regroup_v2_test.go` exercises authority/version/replay rules in Core tests; it is not Android-to-Hub acceptance.

OpenAPI models `/v2/client/rpc` as one encrypted packet endpoint and maps operation body/result schemas; operation-specific JSON schema coverage is not a substitute for Android interoperability. Before any of these capabilities is presented as active, add exact native DTO validation and route wrappers, enforce current public and encrypted capability intersections, clear transient proposal/proof data on profile-generation change or app background, ignore late callbacks from the old scope, and implement operation-specific response-loss/revocation reconciliation. Keep real writes disabled until the relevant native/server proof and current-authority path is accepted. No v1 bearer fallback is permitted.
