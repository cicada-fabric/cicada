# Network M1 service contract

**Status:** M1 implementation contract. This document describes the new Network surface; the frozen Android Hub v1.3 catalog, wire version, and capability advertisement are unchanged.

## Authority and scope

A Hub is authoritative for each Network it hosts. `hub_id` and `network_id` are distinct from the physical Node or machine name. A process may host Hub and Node responsibilities together. The Network selector on a request never supplies caller identity or a grant.

Network membership, Endpoint enrollment in a Network, Group membership, and the native SessionBinding are separate. A Network-only Join can register an existing native Thread without creating a Group or a second native writer. The `binding_id` and `binding_epoch` in `NetworkJoinResult` identify only the Network access session; they are not a native writer SessionBinding or a permission to inject into the Thread. Each Group maps to exactly one Network after activation. Pending or ambiguous Group mappings fail closed at Network-scoped operations. Existing Group paths derive their Network from the trusted server-side Group mapping and current binding; an omitted `network_id` cannot bypass the Network Guard.

The M1 directory card contains only the Network ID, Endpoint ID, Network nickname, approved capabilities, and freshness-qualified availability. `ACCESS_RECENT`/`UNKNOWN` reflects Network access recency, not proof that a native Runtime is online. The card excludes workspace, native Session/Thread ID, Node address, binding, private Group membership, Task and history. Resolve filters by the current member's discovery grant before matching; multiple matches return `AMBIGUOUS` and no chosen Endpoint.

## Join evidence

An explicit Network Join requires both a current, one-use invitation for the exact target Owner and a distinct Owner-signed Join grant. The grant uses the Owner ML-DSA identity already registered with the Hub; the private key remains on the Owner's trusted machine. Its signed claims bind a fixed domain, `hub_id`, `network_id`, `owner_id`, Node locator, native Session ID, invitation digest, requested grants and disclosure, expiry, and random nonce. The Hub verifies the registered current Owner key and consumes the grant transactionally. A replay of the same grant for the same already joined native Thread may return the same Endpoint and Network registration; a conflicting use is rejected. A Network administrator may issue an invitation under a current scoped grant, but cannot sign the Owner grant or approve local effects.

The Node's owner-only local bridge verifies the real native Session record before it forwards Join with its Node credential. A model-supplied `approved` flag, Owner ID, Node ID, sender or role is never proof. A signed grant does not replace Node credential validation, and a Node credential does not replace Owner approval. Session credentials are kept separate for Group and Network-only registration; Network credentials cannot call old Group APIs.

## HTTP operations

| Operation | Authentication | Behavior |
|---|---|---|
| `POST /v2/fabric/node/networks/join` | `CicadaNode` credential | Explicit Join for a locally verified native Session using invitation and Owner grant. The Node identity is derived from its credential. |
| `POST /v2/fabric/node/networks/renew` | `CicadaNode` credential | Renew the same Endpoint's Network access after the Node reverifies the original native Session. It rechecks current membership, Owner key, and Node binding; it cannot add grants or create a new member. |
| `GET /v2/fabric/networks/{network_id}/directory` | `Cicada-Network-Session` credential | Returns only cards discoverable by the current Network Actor. `network_id` selects an already joined scope. |
| `POST /v2/fabric/networks/{network_id}/resolve` | `Cicada-Network-Session` credential | Resolves one filtered Endpoint ID or nickname. No existence oracle for hidden cards. |
| `POST /v2/fabric/networks/{network_id}/invitations` | `Cicada-Network-Session` credential with `network.admin.invite` | Issues one scoped invitation for `target_owner_id`, exact `grants` and bounded `ttl_seconds`. Issuer comes from the current Actor. The invitation token is returned only once and gives no Owner consent. |
| `POST /v2/fabric/networks/{network_id}/leave` | `Cicada-Network-Session` credential | Revokes this Endpoint's Network registration without replacing its native Thread or unrelated Group registration. |

Network provisioning and Group migration mapping/activation use a local operator CLI against an existing Hub database. The Network Owner must already be an active human Principal with an independently registered Owner approval public key; the existing `owner-key register` command provides that local trust setup. `cicada network create --db DB --hub HUB --name NAME --owner OWNER [--network ID]` creates a Network; `list --db DB` shows Networks and phase. `migration-dry-run --db DB` produces a read-only report. `map-prepare --db DB --group GROUP --network NETWORK --expected-version VERSION --reason TEXT` writes a `PENDING` candidate; `map-quarantine` marks one unresolved Group pending; `map-approve` commits the exact mapping, and `activate` turns on the Network Guard. An approved Group cannot be remapped. `member-revoke` requires the current member revision; `invite` and `invite-revoke` use a private token file. The global management bearer identifies an operator, not an Owner, and can never create Owner consent. A Network-only credential has no device command, private key, native history, machine execution or user approval authority.

The Owner signs locally with `cicada network consent-sign --owner-private FILE --proof-file FILE --invitation-file FILE --owner OWNER --hub HUB --network NETWORK --node NODE --session SESSION --grants exact,grants [--discoverable]`. The proof and invitation files have mode 0600 in a private directory; neither secret appears in CLI JSON output. The original Session joins through `cicada network join --network NETWORK --invitation-file FILE --proof-file FILE --session-state-file FILE`, using a verified local Node socket. `network directory`, `resolve`, `renew`, and `leave` read that separate private Network session file. MCP offers corresponding Network tools; its invitation/proof paths come only from trusted local settings, never model arguments. Access renewal rotates the Network credential without asking for another invitation or Owner signature. A revoked member cannot renew.

For MCP, configure existing private directories `CICADA_NETWORK_JOIN_DIR` and `CICADA_NETWORK_SESSION_DIR` on the Node, then run `cicada network mcp-scope --network NETWORK` in the exact native Session (or pass its `--session`, `--workspace`, and `--node`). The command prints three paths without secrets. Place the invitation and Owner proof at the printed invitation/proof paths in a private 0700 scope directory; the MCP session state directory is created privately by the tool. The scope hash includes the normalized Hub API origin, native Session ID, harness, and Node ID, so two Threads on one Node cannot share one Network credential file. Join and renew serialize writes under a private lock file, and Network credential requests refuse redirects.

## Guard and transport

Every directory read, resolve, old Group entry, Link route, Relay enqueue/claim, local delivery and native injection checkpoint rechecks the active Network and current membership revisions. Revocation prevents new authorized reads/writes and connected delivery; already delivered ciphertext or native context cannot be recalled. Existing sealed Group and bilateral Owner-approved Link transport remains the private-message path in M1. For a Link, each endpoint must have its own authorized Group scope mapped to the same Network; the endpoints need not share one Group. A Network-only member without a Group cannot use that Link or send a private message in M1. M1 adds no plaintext peer send route, implicit Group, Hub-to-Hub relay, Journal, or new native writer.

The new HTTP and CLI surface is independent of Android Hub v1.3. Public capabilities continue to mean availability only; encrypted device session claims and the server Guard remain authoritative for existing Client operations.
