# Resource Lease release boundary

CICADA.md §18 requires Acquire, Renew and Release to share an atomic resource authority. Native peers may now POST `/v2/fabric/leases/{lease_id}/release` with only `fencing_epoch`, authenticated by the existing CicadaSession. The response is the existing ResourceLease representation. Release carries no content body and introduces no content flow. This native Fabric route introduces no Android operation, catalog, contract revision, database migration or Control peer dependency.

Only the trusted NativeActor Store entry point is exposed for Release. The Store obtains the serialized SQLite writer transaction before checking the current Group `task.claim` grant, principal/endpoint, membership revision, native binding epoch and lease owner, mapped Network membership and the resource holder. Cached authorization cannot replace this transaction check.

For an ACTIVE, unexpired, exclusive `managed_blob` lease with matching executor enforcement and current authority, Release atomically sets the historical lease to RELEASED and the authority to AVAILABLE with no current lease. It preserves the fencing epoch, original expiry, holder fields, existing blob and writer provenance. All managed writes use the same serialized authority boundary: a write may finish before Release, but no publication using the released lease is admitted afterward. The next Acquire advances the retained epoch by one.

An exact authorized retry is a no-op only while the authority still has the released lease's epoch and no successor. It does not extend deadlines or change timestamps. After reacquisition, even the original holder's old retry is stale and cannot release the new lease. The current Guard is checked on every retry.

GPU and workspace leases remain advisory. Expired, uncertain, quarantined or inconsistent state is not proof that a process stopped. Release refuses these cases without changing authority. Existing trusted-management Reconcile checks the authorized caller's supplied stop attestation and evidence under Guard; it does not itself stop or independently verify an external process. This change does not add an external executor or claim strong resource isolation.

The existing `write-managed-blob` route accepts a plaintext value and stores it in Hub SQLite. This is Hub-managed executor state, not sealed peer Relay or E2EE artifact storage; the bodyless Release route adds no content flow. At the release checkpoint, Acquire checked the current Task claim, while later resource operations did not re-read Task ownership. The subsequent [Task epoch fence](architecture-v2-resource-task-epoch.md) supersedes that execution/renewal boundary: Renew and managed Write require the exact live acquisition Task ownership generation. Release and Quarantine retain independent cleanup permission; loss of Task ownership does not make the physical resource available. Historical release validation below remains attributed to its tested source.
