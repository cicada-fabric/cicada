## Fast local function check

On Linux/amd64 with Docker Engine, the package README has the exact offline `docker load`, image-ID check, and run command. It binds `serve --host 127.0.0.1 --port 8787` on Linux host networking and mounts a fresh named volume at `/state`. The Hub runs as UID/GID 1000; a fresh Docker volume receives the image's `/state` ownership through normal initial copy-up. `docker stop "$TRIAL_NAME"` stops it while preserving the named volume. This loopback HTTP check is intentionally local and does not configure strict PQ TLS.

With the Hub running, the README gives the foreground Node command using the included Linux/amd64 package, loopback URL, new machine ID, private state directory, and relay mode. The direct relay-only command does not need the Codex Runtime. Native execution needs the user's existing Runtime; the optional `scripts/install-cicada-worker.sh` helper also checks for `codex queue`. The standard Linux/arm64 CLI is included separately for baseline-only testing; it is not a PQ Node build.

Node pairing and Native use have separate authorization and context steps. Inspect the exact pending Node in encrypted Client `nodes.preview`, then call `nodes.confirm`; a device code alone is not authorization. Pairing does not join a Thread or Group. For Native use, start in the existing intended Thread, explicitly call MCP `cicada_join`, check `cicada_whoami`, and preserve the exact Thread ID/context. Positive and refusal tests should use a disposable Group and cover pre-confirmation, missing grant, wrong Group, and revoked grant cases. See [native join/binding validation](native-network-join-binding-validation.md), [permissions](permissions.md), and [Client/Hub interop](client-hub-interop-v1.md).

Client-Control uses its documented NIST application-layer suite, but that alone does not make Hub↔Node transport pure PQ. The retained PQ Hub plus two shipped Linux/amd64 Nodes passed the scoped protocol gate. The reported topology also includes an Android phone; it needs an independently built Client compatible with contract 1.6.5 and a reachable HTTPS Hub. No APK is bundled or attributed to d86; the Android artifact producer is the separate `CICADA_CLIENT` repository. Android physical-device, public HTTPS, real Native Runtime with this PQ Hub + PQ Node combination, and user-environment runs remain NOT_RUN. A separate scoped Native Board A8 pass used the distinct standard A1 image `sha256:c536225d6efeb1e94a83fc44b3abc0d38f59cf266c82e53ce439f9f8b097d73c`; it does not qualify this PQ combination.

## Requested remote topology remains blocked

The reported target is Ubuntu 26 Hub (architecture not yet confirmed), one Linux/amd64 Node, and one Linux/openEuler/aarch64 Node, and an Android phone as Client, with IP-only access required. The current pure-PQ delivery cannot satisfy that topology: the shipped PQ Node package is Linux/amd64 only; the current product PQ Origin/dialing flow still requires DNS and lacks an authorized IP-locator installation/dial configuration; the certificate profile currently uses DNS SAN; and the retained PQ Hub was qualified by an amd64 protocol-gate run. The standard `cicada-linux-arm64` artifact and its third-party notices are present for baseline testing only and must not be described as a pure-PQ Node. No arm64 PQ package or synthetic D1 configuration is included.

The G4 source audit confirms low-level `pqtls.DialContext` can connect an IP socket while independently verifying `HubDNSName`, `HubID`, and pin. The missing piece is the product-approved IP locator and its authorized installation/dial configuration; the current certificate profile uses DNS SAN. A future path may separate IP locator from Hub identity or use a reviewed IP-SAN profile, while preserving all identity checks. A remote pure-PQ trial also needs a real Owner-approved D1 Hub config and Node `active.json` provisioned securely outside this package, a PQ arm64 Node package before both Nodes can participate, and confirmation of the Hub architecture. This package does not provide a ready-to-run end-to-end initial enrollment and certificate provisioning workflow or one-line remote installer; existing trusted offline D1 primitives require independently authorized setup. The IP-only constraint remains a product requirement; DNS substitution is not assumed. Before that follow-up deployment, provide the Hub IP/architecture and whether it is a fresh isolated Hub or an existing stateful service; the local example always uses a fresh named volume. Do not place real private keys, grants, or deployment credentials in this delivery directory.

No real credentials, grants, private keys, Hub/Node state, model/provider data, or source checkout are in the portable archive. The exact local index checksums and portable archive hash are reproducible with the artifact files; no software was rebuilt and no service was started while preparing this package.
