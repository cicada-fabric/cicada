# M2 Group Journal and Discussion contract

**Checkpoint:** 2026-09-30, implementation candidate based on clean `dev` `7c4194155d6c0c342671299e447c907f0b1d94d6` plus the current dirty worktree. This is the authoritative M2 Hub/Node/MCP contract; acceptance evidence belongs in the status and validation records. It does not change Client `client-hub-v1.4` management catalog, encrypted Client wire v1, or Android content UI.

## Authority and scope

One record belongs to one `(hub_id, network_id, group_id)` on its single authoritative Hub. M2 accepts only an `ACTIVE` Network and mapped `ACTIVE` Group whose owner matches each participating Endpoint owner. A cross-owner board has no M2 encryption or consent semantics and fails closed. Each request is bound to a current original native Thread, Node device credential, Group SessionBinding, Endpoint, binding epoch, membership, Group join, Network registration, lease and the relevant independent Group grant. `space.read` permits current reads and is also required of an author; `space.write` permits Journal, topic and reply writes; `space.moderate` permits versioned resolve/reopen. Network membership and a key grant alone grant none of these actions. A public capability advertises implementation, never caller authorization.

The trusted Node bridge checks the original Codex session record and current Hub `whoami`, and keeps Node bearer and Endpoint private keys out of MCP and model tool arguments. It independently validates current or historical Owner key proofs against its local Owner public-key trust. The Hub stores each recipient's NIST ML-KEM/AES-GCM sealed envelope, ML-DSA signatures and minimal metadata; it never receives a Journal or Discussion body in plaintext. A read projection includes the original producer evidence and only the caller's reader evidence/envelope, plus necessary history proof when applicable. MCP returns at most the decrypted body and bounded record metadata to the authorized current Thread. It does not inject into a model queue or wake a Runtime.

## HTTP and native surface

All routes below are `POST /v2/fabric/node/spaces/{route}` with strict JSON. Every call requires `Authorization: CicadaNode <node-token>` and `Cicada-Space-Session: CicadaSession <joined-group-session-token>`; neither is a model argument. The Node credential and Session must resolve to the same current Endpoint/Node. A missing or invalid credential never falls back to a plaintext endpoint or a management bearer.

| Route | Request | Result and guard |
|---|---|---|
| `prepare` | `{group_id,operation_id,kind,topic_id?,corrects_id?,expected_topic_version?,status?,retention_class?}` | Fixed reservation snapshot with record ID, Group-local sequence, exact current reader set and digest, producer/reader signed key evidence, retention deadline and five-minute reservation deadline. Requires `space.write` or, for `TOPIC_STATUS`, `space.moderate`, plus `space.read`. Exact retry returns the original snapshot. |
| `commit` | `{reservation_id,reader_ciphertexts:[{endpoint_id,key_id,wire}]}` | One committed reader projection. Hub checks exact snapshot set, cryptographic outer signature/context, current Guard and, for topic state, version CAS in one transaction. Identical ciphertext retry returns the same record; different bytes conflict. |
| `list` | `{group_id,kind?,topic_id?,cursor?,limit?}` | `{records,next_cursor?}`, at most 16 projections. Cursor is scope-bound, opaque and never an authorization token. `space.read`, current lease/fence and per-Endpoint read cutoff are checked again. |
| `get` | `{group_id,record_id}` | One caller-only reader projection, under the same fresh read Guard and cutoff. |
| `history/manifest` | `{group_id,record_id,recipient_endpoint_id,owner_key_id}` | One frozen candidate for a current old reader and one current new reader: exact original ciphertext digest, recipient key/binding/join/Network revision and evidence digest, one-hour-or-shorter expiry, original caller envelope. This prepares no permission. |
| `history/grant` | `{manifest_id,owner_proof,reader_ciphertext}` | Current old reader submits the separately Owner-signed exact manifest and one newly sealed recipient envelope. Hub verifies Owner signature, recipient/resharer current Guard, one-record cutoff, same key/revisions and exact ciphertext retry before writing. |

`kind` is `JOURNAL`, `TOPIC`, `REPLY`, or `TOPIC_STATUS`. A Journal correction appends with `corrects_id`; a Discussion topic starts `OPEN`, replies refer to its topic ID, and `TOPIC_STATUS` sets `OPEN` or `RESOLVED` with `expected_topic_version`. Resolve/reopen changes discussion state only; it neither accepts a Task nor approves an external action. The Node MCP surface is `cicada_journal_append/list/get`, `cicada_discussion_topic_create/reply/list/get/resolve/reopen`, and `cicada_space_history_manifest/share`. Group selection is the already joined `cicada_use_group` scope; no write tool accepts a sender, arbitrary Group or Owner decision from model text. The existing private MCP outbox supplies a stable operation ID and immutable input for explicit `cicada_operation_retry`; Node fsyncs exact per-reader wire before commit so a lost commit response does not reseal or widen readers.

HTTP failures are bounded and distinct: malformed/invalid `400`, missing Node or Group Session credential `401`, current Guard or pre-cutoff history denial `403`, missing record/manifest `404`, idempotency/version or reader-key-readiness conflict `409`, and Group quota `429`. A `409` or quota `429` is a terminal M2 outbox failure for that attempt, not an automatic blind retry; transport loss, timeout or `5xx` remains `UNKNOWN` with explicit original-byte retry.

Journal, topic and reply bodies are 1–16 KiB; `TOPIC_STATUS` accepts no caller body and seals a bounded Node-generated status payload. Reader count is 1–32 including author, and page size is at most 16. A genuine synthetic 32-reader Owner-proof snapshot serialized to about 1.49 MB; with 16 KiB body, its commit JSON was 2,116,357 bytes and 16 projected records occupied 2,530,333 bytes. Store accepts a snapshot up to 2 MiB; the Node/HTTP commit request and list response cap are 4 MiB, while the Unix bridge returns only plaintext projections. The three retention classes are `short` (24 hours), `week` (7 days), and `standard` (30 days, default). The Hub enforces per-wire and aggregate ciphertext quotas, and retention purges content and keeps at most 4,096 tombstones per Group for at most 30 days after purge. Exact duplicate/conflict protection lasts while the original record or its tombstone exists; it is not a permanent operation-ID registry. After that bounded window, a trusted author may reuse the same operation ID only to create a newly signed record with a new record ID and cryptographic context. A purged old record ID and its old sealed context cannot be revived. The private Node sealed cache and M2 MCP outbox preserve retry material through the maximum retention, then prune opportunistically and impose local quotas. `operation_id` remains scoped by Hub, Network, Group, Endpoint and kind; `record_id`, cursor and topic version cannot authorize by themselves. Exact thresholds and error codes are implementation invariants, not a promise that quota exhaustion succeeds.

## Single-record history decision

A member who disconnects but retains `space.read` and its original cutoff can fetch missed retained records normally. Losing and regaining that grant establishes a new `read_from_seq`; joining later never opens earlier ciphertext. A currently authorized holder of the old signed body obtains `cicada_space_history_manifest` for one old record and one current later reader. The human Owner reviews the manifest and, on a trusted machine with its existing `0600` private key, runs `cicada owner space-history-sign --private FILE --manifest FILE --expect-owner-id ID --expect-record-id ID --expect-recipient-endpoint-id ID`. The command emits a base64 `owner_proof`; its signed manifest ID is parsed by the Node, so no request ID is retyped. A model assertion or ordinary Group Endpoint key grant cannot stand in for this signature.

The old reader passes that proof to `cicada_space_history_share`. Its Node independently verifies locally pinned Owner public identity, exact signed scope, original digest, new reader key and evidence, current Guard and original inner producer signature. It reuses the exact original signed body but seals a fresh reader envelope signed by the resharing Endpoint and bound to the history grant ID. On later `get/list`, the recipient Node checks the Owner proof against local trust, original producer signature, resharing signature, historical key evidence at the signed times, current Guard and grant expiry before returning plaintext. The Hub stores no plaintext or reusable Group history key. The recipient cannot read a different old record, another Endpoint's material, or this record after current read authorization or retention expires. Already copied plaintext cannot be recalled.

M3 cursor hints/notifications, M4 topology regrouping, M5 multi-Hub/Client changes, Android board contents, full-text search, general chat and Runtime wake are outside M2. Client v1.4's existing management operations continue unchanged; M2 HTTP/MCP is an internal native Node surface, not an Android content contract.
