# Client ↔ Hub wire contract (server implementation)

This document describes the **implemented Hub side** for the separate Android repository. Packet framing is version 1. The public capabilities response advertises `contract=android-hub-v1-draft` and `status=partial` (or `not_ready` when Control is unavailable); the separate pinned identity document uses `contract=android-hub-v1`. These names serve different endpoints and are both current. Read `GET /v2/client/capabilities` first: use only operations listed in `available_rpc_operations`, and gate optional flows on their capability flags. A `true` flag reports a Hub implementation; it does not claim that an independent Android implementation has passed interoperability testing. In particular, `status_events` and `external_thread_links` remain `false`. The Hub combines Control, Directory and Relay in development, but only Control decrypts these management packets. Peer Endpoint messages use a different identity and must not enter this RPC.

## Client contract at a glance

The Android Client talks to Hub metadata endpoints for capability negotiation and pinned identity, enrolls one device with an owner-signed grant, then sends sensitive reads and writes only through encrypted `POST /v2/client/rpc`. The route names the operation and binds the packet to Hub, owner, device, session epoch, sequence and operation ID; the encrypted body carries the operation input. The Hub derives the trusted owner and device from its enrollment store, not from route claims. Do not substitute the legacy management bearer APIs for this flow.

The Client RPC terminates at Control because Control must read management requests to plan and manage work. This protection does not make ordinary Endpoint↔Endpoint messages end-to-end encrypted: those messages do not use this RPC, and the existing Fabric peer path is still not Hub-blind E2EE.

## Bootstrap and trust

Run `scripts/run-client-hub-dev.sh` from this repository for a local Docker Hub; it binds `127.0.0.1:8787` and keeps its state under `.cicada-data/client-hub-dev`. `GET /v2/client/capabilities` and `GET /v2/client/identity` are public metadata. The latter returns stable `hub_id`, `control_public_identity`, `control_key_version=1`, and the suite. The Android app must pin the Hub ID and full Control public key through an independent trusted channel. Downloading that JSON over an untrusted URL does not establish trust.

The current capability values are deterministic. With Control enabled, `legacy_management_api_available`, `client_control_pq_e2ee`, `authenticated_client_session`, `status_snapshot`, `topology_management`, `status_changes_partial`, `control_intents`, `device_binding`, `link_key_consent`, `client_device_enrollment`, `client_device_management`, and `approval_read_and_decide` are `true`; `status_events` and `external_thread_links` are `false`. `available_rpc_operations` then contains `status.snapshot`, `status.changes`, `topology.snapshot`, `topology.apply`, `devices.list`, `devices.revoke`, `nodes.preview`, `nodes.confirm`, `nodes.list`, `nodes.revoke`, `approvals.list`, `approvals.decide`, `intent.get`, `intent.status`, `intent.list`, `intent.submit`, `link.key_manifest`, `link.key_grants`, and `link.key_grant`. Without Control, status is `not_ready`, the operations list is empty, and every capability flag is false. `legacy_management_api_available` only indicates that legacy handlers exist; it does not make their bearer API part of the Android contract.

The Hub creates its self-owned Human Principal from its persistent Control identity on first startup; this does **not** create a Group, join a Thread, or register an Android device. The operator must independently register an owner ML-DSA public key in the local Hub database with `cicada owner-key register --db ... --owner-id ... --public ... --expect-key-id ...`. The private owner key stays with the owner. There is no bearer-token HTTP shortcut for this trust bootstrap. A trusted owner key signs one exact `OwnerDeviceGrant` for the device's independent ML-KEM/ML-DSA public identity. `POST /v2/client/devices/enroll` verifies that signature, its 32-byte nonce, Hub ID, key fingerprint, purpose `CLIENT_CONTROL`, issuance/expiry, and owner scope; a nonce is consumed once. The response gives `session_epoch=1` and `device_key_version=1`. Losing a device requires a different enrolled device or trusted local recovery to revoke it; a current device cannot self-revoke inside its own encrypted session because its accepted response would become undeliverable.

The public identity JSON fields are `id`, `kem_public`, `signing_public`; binary fields use standard padded base64. `id` is `pq1-` plus the first 16 bytes of SHA-256 over the concatenated ML-KEM and ML-DSA public key bytes, hex encoded. Device key enrollment binds a SHA-256 fingerprint over `"cicada/client/device-public-key/v1\x00" || compact_public_identity_JSON`. See `internal/e2ee/owner_device_grant.go` for the exact signed claim order and `internal/server/client_v2.go` for HTTP shape. The current Go test is a protocol producer, not a claim that an independent Android implementation has passed interop.

## Encrypted RPC packet

All sensitive Client reads and writes use `POST /v2/client/rpc` with `Content-Type: application/json` and an application-layer packet:

```json
{
  "route": {
    "version": 1, "direction": "REQUEST", "hub_id": "hub_...",
    "owner_id": "pq1-...", "device_id": "phone-a",
    "session_epoch": 1, "sequence": 1, "operation_id": "unique-client-operation",
    "operation": "status.snapshot", "sender_key_id": "pq1-...",
    "sender_key_version": 1, "receiver_key_id": "pq1-...",
    "receiver_key_version": 1
  },
  "envelope": "BASE64_OF_COMPACT_ENVELOPE_JSON"
}
```

The route uses the field order in `internal/clientwire/wire.go`; its compact Go JSON is authenticated associated data prefixed with the literal UTF-8 bytes `cicada/client-control/packet/v1\x00`. The inner envelope has version 1 and algorithm `ML-KEM-768+ML-DSA-65/AES-256-GCM`. Sender encapsulates to the pinned receiver ML-KEM-768 key; HKDF-SHA256 derives 32 bytes from the shared secret with zero salt and info `cicada/e2ee/v1/key || sequence_u64_big_endian || route_AAD`. AES-256-GCM uses a fresh random 12-byte nonce and associated data `route_AAD || compact_envelope_header_JSON`. The sender signs the compact unsigned envelope JSON with ML-DSA-65. Exact header, envelope field order, omission rules and verification are defined in `internal/e2ee/pq.go`. Android must reproduce those bytes precisely; do not sign a generic map with arbitrary key order.

The Hub looks up owner, device, current public key and session epoch from its Store **before** accepting the packet. Route fields only select a record; they cannot grant authority. Request sequence starts at 1 and increases by one per device epoch, with a stable `operation_id` per logical action. The sender persists its next sequence and exact sealed packet before transmitting. An exact byte-for-byte retry gets the identical cached sealed response; a changed packet at the same sequence or reused operation ID is rejected. A duplicate while the first request is still running receives HTTP 409 and does not cancel the first request. Restart fences an unfinished synchronous RPC as `UNCERTAIN`; the Client must query authoritative state with a **new** operation after reconciliation, not blindly submit the action again.

A successful HTTP 200 body is a signed, encrypted **RESPONSE** packet to the device. It keeps the operation and operation ID, swaps sender/receiver key IDs and versions, and uses the Hub's own monotonically allocated response sequence. After decryption the body is:

```json
{"request_id":"clientreq_...","operation_id":"unique-client-operation","ok":true,"result":{}}
```

When `ok=false`, `error` replaces `result`; this is a business rejection protected inside the packet. The field is currently a free-text string. There is no stable RPC `error_code`; an Android client must not branch on these strings. Such a rejection still uses HTTP 200 and consumes the accepted request sequence. By contrast, transport/authentication failures use HTTP errors shaped as `{"error":"..."}` (server errors replace the message with `internal server error`): `400` is a malformed, empty, or oversized packet; `403` is an inactive/untrusted device or failed signature/key/session binding; `409` is a replay, sequence, operation-ID, session-epoch, in-progress, or uncertain-state conflict; `405` is a wrong HTTP method; `503` means Control is unavailable; and `500` is an internal response-sealing/serialization failure. Enrollment has `400`, `403`, `405`, and `503` outcomes. The public Node code route has `400`, `405`, `409`, `429`, and `503` outcomes. Neither public route uses a legacy bearer as authority. The Hub does not put the plaintext operation body in its default logs or the replay table. Maximum outer packet is 256 KiB; maximum decrypted operation body is 64 KiB.

## Available operations

| `route.operation` | Encrypted request body | Result and current boundary |
|---|---|---|
| `status.snapshot` | `{}` | Typed Node/Endpoint/native Session/Worker/Goal/Group/Task projection. Single owner database only; statuses include source, observed time and stale/unknown. Nodes include `verified` from the owner binding. |
| `status.changes` | `{"cursor":"...","limit":100}`; omit cursor for first page | Durable owner-bound cursor over snapshot-derived Node/Endpoint/Worker/Goal/Group/Task changes. Omitted or non-positive `limit` defaults to 100; values above 500 clamp to 500. Returns `completeness:"partial"`; excludes approvals, intents, link/membership events and transitions between reads. Poll this operation and reconcile with `status.snapshot`. |
| `topology.snapshot` | `{}` | Owner-scoped Group, Membership, Endpoint and same-owner Link metadata; no prompt, credential, key or peer payload. |
| `topology.apply` | Tagged action; see below. | One owner action at a time. Object-specific CAS; Link proposal remains `PROPOSED`, never grants routing. |
| `devices.list` | `{}` | Owner's registered device public identities, state and versions. |

| `intent.submit` | `IntentInput`: required `text`; optional `kind`, `target_id`, `decision`, `revisit_when`, `attachments` (string array), and `goal` (`GoalInput`). Object field order is significant only where a cryptographic canonical byte form is called out; ordinary result JSON is parsed as JSON. The current single-owner database limit applies to all these Client projections and operations.

The `link.key_*` RPCs are restricted to `single_owner_control_database`. Current Client topology and Link proposal checks reject cross-owner Links, so the source and target sides here do not represent two independently managed Users. `link_key_consent=true` means these Hub records are available; it does not mean cross-owner consent or external Thread links are implemented.

`topology.apply` uses a tagged union with exactly one matching payload. The supported `kind` values are:

| `kind` | Required payload fields |
|---|---|
| `group.create` | `create_group: {group:{name, purpose?, policy_ref?, context_policy?, isolation_profile?, external_mode?}, parent_group_id?}` |
| `group.set_parent` | `set_parent: {group_id, parent_group_id?, expected_group_version}` |
| `endpoint.join_group` | `join_group: {endpoint_id, group_id}` |
| `endpoint.leave_group` | `leave_group: {endpoint_id, group_id, binding_id, expected_binding_epoch}` |
| `membership.bind_role` | `bind_role: {group_id, membership_id, role, expected_membership_version}` |
| `link.propose` | `propose_link: {proposal:{source_endpoint_id, source_group_id, target_endpoint_id, target_group_id, direction, actions, data_scopes, transport_hub_id?, expires_at}}` |
| `link.revoke` | `revoke_link: {link_id, expected_link_version, reason?}` |

The outer object is `{"kind":"...", ...one payload...}`; unknown outer fields are rejected and the payload name must match `kind`. Group creation defaults `context_policy=group_scoped`, `isolation_profile=trusted_host`, and `external_mode=monitor_mediated` in the existing Control implementation. Use `role=member` to remove an execution role. Group creation plus parent assignment currently uses two Store steps; if the second step fails, the new root Group remains and must be reconciled. `topology.apply` only proposes/revokes same-owner Links. The `link.key_*` operations above can record key-bound owner consent for a current Link, but do not implement external-Link approval or activation.

For `link.key_manifest`, first verify the contract bytes and both Endpoint candidates yourself; do not sign a grant just because the Hub returned a digest. `contract_canonical` is base64 of the canonical Link contract JSON bytes, and `contract_digest` is lowercase hex `SHA-256(UTF-8("cicada/communication-link/proposal/v1\x00") || contract_canonical_bytes)`. The manifest `digest` is lowercase hex `SHA-256(UTF-8("cicada/communication-link/key-manifest/v2\x00") || compact_UTF8_JSON(claims))`; `claims` excludes `digest` and keeps this field order: `version`, `link_id`, `link_version`, `contract_digest`, `contract_canonical`, `source`, `target`. Within each side, the compact JSON field order is `endpoint_id`, `group_id`, `principal_id`, `owner_id`, `node_id`, `binding_id`, `binding_epoch`, `candidate_version`, `key_id`, `key_fingerprint`, `proof_digest`, `public_identity`, `attestation`. JSON `[]byte` fields use standard padded base64. See `internal/store/communication_link_key_manifest_v2.go` for the canonical DTO order.

The contract bytes use this exact field order: `link_id`, `source_endpoint_id`, `source_principal_id`, `source_group_id`, `source_owner_id`, `source_node_id`, `target_endpoint_id`, `target_principal_id`, `target_group_id`, `target_owner_id`, `target_node_id`, `direction`, `actions`, `data_scopes`, `transport_hub_id`, `expires_at`, `scope_snapshot`. `scope_snapshot` fields are ordered `source_membership_revision`, `source_join_revision`, `source_group_version`, `target_membership_revision`, `target_join_revision`, `target_group_version`. Parse these terms and correlate them to the exact Link and current Endpoint/Principal/Group/Node/SessionBinding identities being approved; preserve the canonical bytes when recomputing the contract digest.

The Client must recompute `contract_digest` from the decoded contract bytes, parse and check the complete contract against the current Link it is presenting, recompute each `key_fingerprint` as `sha256:` plus lowercase hex SHA-256 over `UTF-8("cicada/nodekeys/peer-key-fingerprint/v1\x00") || kem_public_bytes || signing_public_bytes`, and verify each ML-DSA-65 Endpoint attestation over the exact public identity and its Endpoint/Principal/Node/SessionBinding ID and epoch. It must also recompute the manifest `digest` from the claims above and confirm both candidate contexts match the source/target identities in the contract. An Endpoint self-attestation proves possession of that Endpoint signing key; it does not establish the User's approval. Only after these checks should the owner sign a time-limited `OwnerLinkKeyGrant` for the intended side. The Hub separately checks the proof against the current owner key, Link version, contract digest and manifest digest. This is key-bound consent storage for same-owner Link records, not proof of routable cross-user consent.

`OwnerLinkKeyGrant` v2 is canonical JSON carried as base64 in `signed_proof`. Its signed claims, in order, are `version`, `owner_id`, `link_id`, `contract_digest`, `key_binding_digest` (the manifest `digest`), `expected_link_version`, `side` (`SOURCE` or `TARGET`), `issued_at`, `expires_at`, and a 32-byte random `nonce` encoded as lowercase hex. ML-DSA-65 signs `UTF-8("cicada/communication-link/owner-key-grant/v2\x00") || compact_UTF8_JSON(claims)`; `signature` is excluded from those claims. The Hub requires canonical UTC timestamps and rejects a grant that expires after the Link. `internal/e2ee/owner_link_key_grant.go` defines the exact v2 shape and checks.

The exact Go DTOs are in `internal/control/client_topology.go` and `internal/control/intents.go`; the encrypted end-to-end Handler tests are in `internal/server/client_rpc_v2_test.go` and `internal/server/client_docker_smoke_test.go`. The latter can target an isolated Docker Hub over TCP. Android does not import Go packages; these files define the current server wire behavior for an independent client implementation.

## Node binding over the Hub

The Node generates `cicada_node_...` locally and stores it in a mode-0600 file. It sends only `fabric.HashSessionCredential(token)` (SHA-256, unpadded base64url) with `node_id` and `node_name` to public `POST /v2/nodes/device-code`. The JSON request has exactly those fields plus `credential_digest`; the response has `user_code` (12 characters grouped 4-4-4) and relative `verification_uri: "/client/device"`. The Hub stores a code digest and pending credential digest. The URI is a path for the separate Android Client to handle; this repository does not serve an authorization UI at that path. The Client must first establish its pinned, owner-authorized encrypted session, then call `nodes.preview` and `nodes.confirm` as separate decisions. Preview returns the pending request's `id`, `hub_id`, `node_id`, `node_name`, `state`, `version`, `expires_at`, and `created_at`; confirm consumes the code once and creates an owner/client-device-bound Node credential binding. After confirmation, the Node can use `/v2/relay/nodes/{id}/events`, `/v2/relay/nodes/{id}/claim`, `/v2/relay/nodes/{id}/receipts`, and `POST /v2/relay/nodes/{id}/heartbeat`. All four routes require `Authorization: CicadaNode <node-bearer>`; `events` is `GET` SSE, `claim` and `receipts` are `POST` JSON, and heartbeat accepts `{}` and returns `204` with no body. Node cannot supply its own status or capabilities through heartbeat. Code expiry is 10 minutes and the Node can request a fresh code while keeping its locally held credential. `nodes.list` includes stored `state`, binding/version fields and current effective `authorized`; an ACTIVE historical binding can have `authorized=false` after its owner key is revoked. Revocation or owner-key revocation stops Relay authentication. The older `/v1/machines/{id}/relay-credential` and `/fabric-deliveries` routes no longer provision or deliver peer traffic.

This binding authorizes the Node's outbound Hub Relay channel with its separate Node credential; it does not expose that credential to Android or make the Node an RPC endpoint. The Hub does not open an inbound connection to the Node: the Node holds the outbound HTTPS/SSE connection. On connect the Hub sends a body-free `ready` event; later wakeups send `event: wake` with `data: claim`. A wake is only a hint. The Node then `POST`s `{consumer_id, limit}` to `/claim`, receives durable delivery records, saves each record in its local inbox/journal, and posts receipts to `/receipts` as it accepts, injects into the exact native session, or records uncertainty/failure. The current claim DTO includes `message_id`, `sender_endpoint_id`, `kind`, `digest`, target `endpoint_id`/`group_id`, `binding_id`/`binding_epoch`, `harness`, `native_session_id`, `node_id`, `attempt_id`, optional `request_id`/`reply_to`/`payload_mode`, and `body`. Current Node implementation accepts only empty or `PLAINTEXT` payload mode and writes the plaintext body into the inbox before native-session injection; this is explicitly not Hub-blind E2EE.

For current bilateral Link trust evidence, an already bound Node may make `GET /v2/relay/nodes/{node_id}/links/{link_id}/authorization` with `Authorization: CicadaNode <node-bearer>`. The request succeeds only when that current Node/owner binding is one side of the Link, the Link's current contract/key manifest is valid, and both source and target owner key-bound grants remain accepted. A `200` JSON body has exactly `manifest`, `source_grant`, `target_grant`, and `link_state`. `manifest` is the `link.key_manifest` object described above. Each grant has `side`, `owner_id`, `owner_key_id`, `owner_public_identity`, `owner_key_state`, `owner_key_version`, `current_status`, and base64 `signed_proof`; `link_state` reports the stored Link state (for example, `PROPOSED`). Node credential failure is `401`, a URL Node ID different from the credential's Node is `403`, and missing, expired, revoked, stale, or incomplete Link authorization evidence is deliberately indistinguishable as `404`. A wrong path/method is `404`; an unavailable Fabric service is `503`.

The bundle is public verification evidence, not an independent trust root and not a route grant. The Node must already trust the owner approval keys through its own authorized trust process, verify both owner proofs against the exact current Link contract, manifest, Endpoint identities and binding epochs, and reject stale evidence. Fetching this bundle does not activate a Link, authorize a message, or expose arbitrary peer data. It does not turn `external_thread_links` on in the Android capability response. This peer-message transport is separate from the Control Worker job queue. A full machine agent obtains assigned Worker jobs and reports results through existing Control machine/worker APIs with a separately configured Control bearer. The agent executes the assigned harness locally in its permitted workspace; Control remains authoritative for Worker and Goal state. Relay-only mode delivers Fabric traffic without those Control-management calls. Android submits management intent to Hub/Control and does not proxy execution to a Node.

Current limitations are advertised by `/v2/client/capabilities`: complete push status event streaming and routable cross-user Thread links are `false`; the newer `link_key_consent` capability is `true` when Control is available, within the single-owner boundary described above. The three `link.key_*` RPCs inspect a current Link/key manifest and record same-owner key-bound consent. They do not implement Client-side external Thread invite/approval, independent two-User consent, Link activation, or routing. Same-owner Client topology cannot create a cross-owner Link. The Node authorization evidence route is a separate Node↔Hub trust boundary; it exposes current public authorization material only to a bound endpoint Node and does not activate routing or make this Client feature ready. The two Endpoint candidates are not yet used for sealed Endpoint-to-Endpoint delivery. `status_changes_partial=true` names the narrower durable snapshot-delta feed. Ordinary Fabric peer messages still use a plaintext legacy path and are **not** Hub-blind E2EE. The legacy `/v1/communication-links` manager-bearer HTTP routes have been retired (they return `404`); Client Link edits use encrypted `topology.apply`. The old `/v1/fabric/*`, manual Thread queue/message and Contact peer ingress routes are retired; their historical SQLite rows remain for migration and audit.
