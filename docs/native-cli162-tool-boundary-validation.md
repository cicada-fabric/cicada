# Native CLI 0.162 tool-boundary audit

This note records a source-level boundary review for the isolated native Worker fixture. It does not change Codex, model metadata, CLI settings, or product policy. The audited upstream source is the official [`rust-v0.162.0` tag](https://github.com/openai/codex/tree/rust-v0.162.0). No local Rust source checkout or source-file SHA was found under the searched `.cicada-data` and `/home/zyf/.cargo` roots, so this note does not claim a local source hash.

## Registration and dispatch

The fixture requests `features.shell_tool = false` and `features.view_image = false`; those feature gates suppress the corresponding shell and image tools in the native tool-router construction. ApplyPatch has a separate registration condition: [`core/src/tools/spec_plan.rs`, `build_tool_router`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/spec_plan.rs#L119-L147) registers it at its [ApplyPatch-specific gate](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/spec_plan.rs#L1272-L1275) when environment tools are advertised and the selected model metadata has an ApplyPatch type. The model field is capability metadata, not an authorization setting.

`code_mode.excluded_tool_namespaces` is applied while building the nested Code Mode tool surface ([`register_code_mode_executors` / `is_excluded_from_code_mode`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/spec_plan.rs#L810-L848)). It does not remove a registered tool from the top-level model-call registry. Top-level `FunctionCall` and `CustomToolCall` items are converted to tool payloads in [`core/src/tools/router.rs::build_tool_call`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/router.rs#L227-L277) and queued from [`core/src/tools/stream_events_utils.rs::handle_output_item_done`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/stream_events_utils.rs#L297-L335); registry dispatch then happens in [`core/src/tools/registry.rs::dispatch_any_with_state`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/registry.rs#L494-L537). The router constructs names as `ToolName::new(namespace, name).with_default_namespace`; default namespace displays as the bare name, while a non-default namespace remains part of the normalized identity ([`protocol/src/tool_name.rs`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/protocol/src/tool_name.rs#L30-L56)).

The registry has a real registration ceiling, `ToolPolicy.allowed_tools` ([`ext/extension-api/src/tool_policy.rs`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/ext/extension-api/src/tool_policy.rs#L1-L38)); registry construction omits tools outside it ([`register_trusted_with_exposure`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/registry.rs#L315-L337)). The core reads it from typed host `ExtensionDataInit` when constructing the session ([`core/src/session/session.rs`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/session/session.rs#L960-L969)). It is not a normal CLI configuration option: the pinned [`core/config.schema.json`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/config.schema.json) has no `tool_policy` or `allowed_tools` field. Therefore this audit does not claim that the current stock CLI fixture can unregister ApplyPatch through its config file.

At the top-level response boundary, a `RespondToModel` error becomes a `FunctionCallOutput` item with an empty call ID and text body ([`core/src/tools/stream_events_utils.rs`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/stream_events_utils.rs#L375-L400), [response conversion](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/stream_events_utils.rs#L515-L536)). The response item alone does not retain the original tool name or call kind. Any zero-runtime diagnostic must classify the source error before serialization and retain only a closed enum, input-call kind, normalized tool name, and response-item kind; it must not persist the message body. A fatal kind mismatch is a separate failure class. No raw provider or tool payload belongs in the evidence.

## Approval and credential boundaries

Ordinary ApplyPatch approval is not a dependable denial boundary. In [`core/src/tools/approvals.rs::request_reviewer_approval`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/approvals.rs#L776-L824), a preapproved permission can return Approved without prompting, and prior patch approval can be reused. MCP approval follows a separate branch. A trusted, control-capable `PreToolUse` hook can target `apply_patch` before the handler, but hook errors and parse failures fail open; it is not equivalent to removing the registry entry and is not claimed here as a guarantee.

The Worker fixed-origin broker is a credential-transport boundary, not a tool authorization boundary: it controls the TLS origin and credential injection, while the HTTPS body is opaque to it. The next implementation step is to keep the real Peer key outside the native container and Node process, reusing the existing fixed-TLS broker as an opaque request/response path. Validate an MCP-positive case and a public synthetic-secret negative case. If the stock CLI cannot close ApplyPatch registration, record that limitation as unsupported; do not change model metadata, global settings, or fork the CLI to manufacture a pass.
