## Registration and dispatch

The fixture requests `features.shell_tool = false` and `features.view_image = false`; those feature gates suppress the corresponding shell and image tools in the native tool-router construction. ApplyPatch has a separate registration condition: [`core/src/tools/spec_plan.rs`, `add_core_utility_tools`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/spec_plan.rs#L1344-L1346) registers it when environment tools are advertised and the selected model metadata has an ApplyPatch type. The model field is capability metadata, not an authorization setting.

`code_mode.excluded_tool_namespaces` is applied while building the nested Code Mode tool surface ([`register_code_mode_executors` / `is_excluded_from_code_mode`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/spec_plan.rs#L852-L895)). It does not remove a registered tool from the top-level model-call registry. Top-level `FunctionCall` and `CustomToolCall` items are converted to tool payloads in [`core/src/tools/router.rs::build_tool_call`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/router.rs#L227-L277) and queued from [`core/src/tools/stream_events_utils.rs::handle_output_item_done`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/stream_events_utils.rs#L297-L335); registry dispatch then happens in [`core/src/tools/registry.rs::dispatch_any_with_state`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/registry.rs#L494-L537). The router constructs names as `ToolName::new(namespace, name).with_default_namespace`; default namespace displays as the bare name, while a non-default namespace remains part of the normalized identity ([`protocol/src/tool_name.rs`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/protocol/src/tool_name.rs#L30-L56)).

For 0.162, the setting belongs under `[features.code_mode]`, not a top-level `[code_mode]` table. `resolve_code_mode_config` reads `config_toml.features` and `code_mode_toml_config` reads `features.code_mode` ([`core/src/config/mod.rs`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/config/mod.rs#L2553-L2562), [helper](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/config/mod.rs#L2814-L2818)); `FeaturesToml` declares `code_mode` under `features` ([`features/src/lib.rs`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/features/src/lib.rs#L807-L815)). The earlier fixture used the unconsumed top-level location. The later table-relocation run strictly confirmed the nested setting and absence of that legacy table; its nested Code Mode result is recorded below and does not change top-level registry behavior.

The registry has a real registration ceiling, `ToolPolicy.allowed_tools` ([`ext/extension-api/src/tool_policy.rs`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/ext/extension-api/src/tool_policy.rs#L1-L38)); registry construction omits tools outside it ([`register_trusted_with_exposure`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/registry.rs#L315-L337)). The core reads it from typed host `ExtensionDataInit` when constructing the session ([`core/src/session/session.rs`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/session/session.rs#L960-L969)). It is not a normal CLI configuration option: the pinned [`core/config.schema.json`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/config.schema.json) has no `tool_policy` or `allowed_tools` field. Therefore this audit does not claim that the current stock CLI fixture can unregister ApplyPatch through its config file.

At the top-level response boundary, a `RespondToModel` error becomes a `FunctionCallOutput` item with an empty call ID and text body ([`core/src/tools/stream_events_utils.rs`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/stream_events_utils.rs#L375-L400), [response conversion](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/stream_events_utils.rs#L515-L536)). The response item alone does not retain the original tool name or call kind. Any zero-runtime diagnostic must classify the source error before serialization and retain only a closed enum, input-call kind, normalized tool name, and response-item kind; it must not persist the message body. A fatal kind mismatch is a separate failure class. No raw provider or tool payload belongs in the evidence.

## Approval and credential boundaries

Ordinary ApplyPatch approval is not a dependable denial boundary. In [`core/src/tools/approvals.rs::request_reviewer_approval`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/approvals.rs#L776-L824), a preapproved permission can return Approved without prompting, and prior patch approval can be reused. MCP approval follows a separate branch. A trusted, control-capable `PreToolUse` hook can target `apply_patch` before the handler, but hook errors and parse failures fail open; it is not equivalent to removing the registry entry and is not claimed here as a guarantee.

The Worker fixed-origin broker is a credential-transport boundary, not a tool authorization boundary: it controls the TLS origin and credential injection, while the HTTPS body is opaque to it. A single no-key host-side PID-namespace proof passed: Docker-inspected host PID 830308 was verified as `NSpid [830308, 1]` in a namespace distinct from the host; one registered PID1 UDS peer was accepted and one same-UID child was rejected as `RELAY_PEER_MISMATCH`. The proof used the pinned image with network disabled, UID/GID 1000, read-only root, dropped capabilities, no-new-privileges, 256 MiB and one CPU. Broker shutdown reported owner stopped, handler/native idle, listener unlinked, and relay pidfd exit observed. The broker's generic `cross_pid_namespace_peer_proof=NOT_VERIFIED` field remains a separate generic status; the proof's own host-side mapping/auth checks passed. The proof did not read or mount a real key and did not exercise HTTP, TLS, provider, model, or CLI behavior, so it does not establish real-key isolation or Native acceptance. Root independently confirmed the exact container ID/name, temporary `p`/`s` directories and CID file absent, six resident snapshots unchanged, and all ten inputs pinned unchanged. Root reran `python3 -B -m unittest -q test_peer_outer_broker test_peer_namespace_proof` on those exact pins: 28 tests passed, exit 0 in 0.131 seconds, with no Docker, provider, or model use in the test run. Docker stop escalation was not recorded, so this does not claim graceful exit or absence of SIGKILL. See the [proof result](../.cicada-data/native-observer-wiring-20261007/peerproof-20261009a001/PROOF.NONAUTH.json) (SHA-256 `f9f0401fe1e6837c8e7c08b5cb435788c06b6d74f437abc72fa73e8d2252e731`) and [PREPARE-REVIEWED4 inputs](../.cicada-data/native-observer-wiring-20261007/peer-outer-broker-20261009a/PREPARE-REVIEWED4.NONAUTH.json) (SHA-256 `215f2c93c61f0bde9cb8bb909b8471e895847af6aa67e924ba0cdbe905805d31`). Next is explicit approved-key-path wiring and trusted-parent Peer integration; the broker remains a private candidate, not a shipping dependency or acceptance result.

## Current table-relocation and registry result

The corrected zero-key input moved only the Code Mode exclusion into `[features.code_mode]`; the strict config projection matched that table and confirmed the old top-level table absent. Its summary matched the expected nine MCP names, reported the excluded local names as not callable through nested Code Mode, kept the synthetic global canary unchanged, and recorded two successful MCP `whoami` calls. This is scoped evidence for the nested Code Mode surface, not removal of top-level CLI registry entries.

An intermediate `PROVIDER_TOOL_SHAPE` result was caused by a fixture decoder that assumed tool definitions were in top-level `tools`. With `use_responses_lite=true`, pinned [`core/src/client.rs::build_responses_request`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/client.rs#L866-L880) places them in a developer `AdditionalTools` input item and sets the Rust `tools` option to `None`; serde omits that top-level field, while the fixture's Python `request.get("tools")` consequently returned `None` and rejected the request. The strict fixture decoder was corrected to read `AdditionalTools` from the input without changing the original input, metadata, feature policy, or any of the nine expected MCP tool oracles. Eight pure synthetic serialization tests passed, and the no-key run observed two successful MCP calls. This resolved the fixture-shape mismatch, not the top-level registry outcome.

The same run ended `NATIVE_ERROR` after `CORRELATED_TOOL_RESULT_OBSERVED`. Four top-level synthetic attacks yielded an aggregate count of six, the sum of `top_level_outputs` and `correlated_output_count`; those counters overlap, and the number of distinct outputs or calls was not persisted. Two outcomes remained unknown. A correlated output does not prove handler entry: in pinned 0.162, registry lookup can return `RespondToModel` for an unsupported tool ([`registry.rs::dispatch_any_with_state`](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/registry.rs#L517-L536)), and `parallel.rs` can turn that failure into a correlated output ([lines 70–104](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/parallel.rs#L70-L104), [288–310](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/core/src/tools/parallel.rs#L288-L310)). Since the fixture did not retain response text or handler-entry evidence, it cannot establish whether those top-level handlers ran or were denied. Top-level tool behavior and credential containment remain **NOT_ESTABLISHED**.
